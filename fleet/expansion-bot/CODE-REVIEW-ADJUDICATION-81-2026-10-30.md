## The one piece of context that changes the grading
All three reviewers' top finding (summary never reconciles, green-with-failures) is **true of the workflow artifact and false of the system**. The workflow header states it and `ingest_results.py` proves it: ingest iterates the checkpoint's expected `job_ids` for the batch; a job with NO result read back stays `packed` and is printed as "still packed (no result read back, NOT guessed)" — the checkpoint never closes a job without evidence, errors bump attempts (terminal at 3). So silent job loss cannot occur at the checkpoint level. What CAN happen: the `batch-summary.json` artifact, read standalone, overstates completeness. Verdict: real hardening worth doing (cheap), severity HIGH→MEDIUM in system context.

## Architecture verdict (the "quicker way")
Unanimous: **no platform replacement is justified** — Gemini A (keep+patch), Perplexity A (keep+patch; test a lease-based worker pool as an unmeasured hypothesis), Claude B (keep + complement). The one materially-faster idea with a mechanism, from Claude and echoed by Gemini's overhead point: **chunked sharding** — pack multiple jobs per runner leg and execute them in an in-runner process pool, amortizing checkout/setup/pip across the chunk; keep one-job-per-leg for heavy jobs. Plus a **VM process-pool drain for tiny tasks** (drain_local.py already imports burst_runner — the seam exists). Perplexity's persistent lease-based worker pool is the same idea at higher complexity; chunking captures most of it inside the current design. Expected effect: removes the fixed per-job overhead that dominates small-task batches; does NOT change heavy-job throughput. This is a dispatcher-side change (pack_batch + runner range mode + workflow matrix over chunks) — MEDIUM effort, build after the correctness patches.
